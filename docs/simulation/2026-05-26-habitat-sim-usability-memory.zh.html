Habitat-Sim 真实仿真操作方案

目标是在进入实车 RGB-D/RTK 之前，把当前的 usability-centered object memory 算法接入 Habitat-Sim / Habitat-Lab 的真实室内场景、深度传感器和导航 episode，获得比 2D Grid Trace 更接近物理传感器退化的验证。

0. 本文边界

要做什么

跑 Habitat 中的 RGB-D + agent pose + ObjectNav episode，提取中间 evidence trace，再复用当前 `UsabilityUpdater` 和 `UsabilityDecisionPolicy`。

不做什么

第一轮不训练模型、不接 GroundingDINO、不追求 leaderboard、不把 Habitat 结果伪装成实车结果。

验收标准

能在至少一个真实 Habitat 场景中生成 `habitat_trace.csv`、`summary.json`、`report.html`，并统计 UNKNOWN / FREE / OCCLUDED / POSITIVE 的比例。

1. 总体路线

Habitat Scene Dataset -> Habitat-Sim RGB-D + agent state -> Object evidence extractor -> intermediate trace schema -> objectnav_core.memory.usability -> trust / verify / search / retire decision report

核心原则：Habitat 只负责产生更真实的传感器和几何观测；算法仍然在 `objectnav_core` 里运行。这样以后替换成 XJTLU rosbag 或实车话题时，不需要改 belief / decision 逻辑。

2. 推荐阶段

阶段 目标 输入 输出 风险
P0 环境 smoke 确认 Habitat-Sim 能启动、RGB-D 非空、agent pose 正常 1 个 scene，10-20 step 截图、深度统计、pose 序列 安装/显卡/数据集路径
P1 Trace replay 把 Habitat 输出转成当前算法需要的 evidence trace RGB-D、semantic 或 oracle object state、agent pose `habitat_trace.csv` 证据定义过强或过弱
P2 Monte Carlo 跑足够多 episode，看 false deletion / ghost / over-verify 多 scene、多 object category、多起点 `summary.json`、`report.html` 参数被 synthetic 过拟合
P3 对照实验 比较 baseline memory 与 usability memory 同一批 episode trace decision/error table baseline 选得不公平

4. 数据集选择

数据集 用途 第一轮建议
Replica / ReplicaCAD 室内几何质量较高，适合调 RGB-D / depth edge / occlusion 逻辑 优先 smoke
HM3D 大规模真实扫描，适合多 scene Monte Carlo 第二阶段
MP3D 历史 ObjectNav 常用，但授权和下载流程更麻烦 非第一优先

第一轮不要追求 benchmark 完整性，只要选一个能稳定加载的 scene，把证据链跑通。

5. Trace Schema

Habitat 输出必须转换成和 2D Grid Trace / XJTLU bag replay 兼容的中间格式。第一版建议字段如下：

字段 类型 来源 用途
`episode_id`string/intHabitat episode分组统计
`step_index`intsimulation step时间顺序
`scene_id`stringscene path跨场景分析
`agent_x/y/z/yaw`floatagent state位姿和视角
`target_category`stringepisode goal 或 oracle object目标类别
`target_x/y/z`floatoracle semantic object只用于评估，不用于算法作弊
`rgb_path`stringoptional artifact人工 debug
`depth_valid_ratio`floatdepth map传感器退化度量
`depth_edge_invalid_ratio`floatdepth map around object mask/bboxflying pixel / hole 风险
`visible_fraction`floatsemantic/oracle visibility区分 POSITIVE / OCCLUDED / UNKNOWN
`ray_free_fraction`floatdepth ray testFREE 证书强度
`evidence_type`enumextractor喂给 usability memory
`evidence_strength`floatextractor控制 belief update 幅度
`quarantined`boolsensor health gateOOD / depth failure 保护
`d_nav/d_verify/c_search`floatgeodesic distance / planner决策成本
`decision`enumpolicytrust / verify / search / retire

6. 证据提取规则

第一版不要用 GroundingDINO。先用 Habitat 的 oracle semantic/object visibility 做上界实验，再逐步替换成真实检测器。否则我们分不清是算法失败，还是检测器失败。

证据 Habitat 条件 算法处理
POSITIVE 目标类别在视野内，visible fraction 高，depth 有效 提高 `P_existence`、`P_location_valid`、`P_usable`
OCCLUDED 目标位置在视锥内，但前方有遮挡面，目标不可见 保持 existence，轻微降低 usability 或不降
FREE 记忆核心体素/区域被可靠深度射线穿过，且 depth health 良好 降低 `P_location_valid` 和 `P_usable`，不直接归零 existence
NON_CONFIRMATION 视角/距离还可以，但没有形成可靠 FREE 或 OCCLUDED 弱负证据
UNKNOWN 视角差、距离远、深度大面积无效、运动模糊或 sensor health 差 不更新或极弱更新

关键保护：depth edge invalid ratio 过高时，禁止生成 FREE。这样专门防 RealSense/Habitat 深度边缘毛刺导致的误删。

9. Baseline 设计

Baseline 含义 为什么公平
Last-Seen Memory 只要曾经看到目标，就一直相信旧位置 检验幽灵记忆问题
Log-Odds Occupancy Memory FREE / HIT 用传统 log-odds 更新 检验“只做占据更新”是否足够
Conservative Unknown 非正证据几乎都 UNKNOWN 检验过度保守导致不清理记忆
Usability Memory 本文算法：分开 `existence/location/usable` 主方法

10. 指标

指标 定义 对应审稿质疑
False deletion rate目标仍存在但 memory 被 retire 或 location_valid 过低FREE 误删
Ghost retention rate目标已移除但 memory 长期保持 usable幽灵记忆
Unknown ratio负面观测中 UNKNOWN 占比过度保守是否等于没更新
Verify ratio决策为 verify 的比例和额外路程是否疯狂验证
Task cost regret相对 oracle policy 的路径/时间差期望成本是否真的有效
Recovery after occlusion遮挡解除后 belief 恢复速度OCCLUDED 死锁
Depth quarantine count因深度健康差拒绝 FREE 的次数OOD 深度崩坏保护

11. 实验矩阵

实验 Episodes 目的 通过条件
Smoke 20 跑通 Habitat 到 trace 到 memory 无崩溃，RGB-D/pose/evidence 非空
Depth Failure 500 深度孔洞和边缘毛刺是否导致 FREE 误删 false deletion 低于 Last-Seen/Log-Odds
Moved/Removed Object 1000+ 幽灵记忆是否清理 ghost retention 明显低于 Last-Seen
Occlusion Stress 1000+ 纸箱/遮挡物前后是否死锁 长期 OCCLUDED 会降 usability 或触发 search
Multi-Scene Monte Carlo 10000+ 统计稳定性 置信区间收敛，决策比例合理

12. 实施顺序

  1. 创建 `configs/habitat/usability_smoke.yaml`，只写路径和传感器参数。
  2. 写 `src/objectnav_core/objectnav_core/evaluation/habitat_trace_schema.py`，定义 trace row dataclass。
  3. 写一个不依赖 Habitat 的单元测试：用 fake RGB-D/depth stats 生成 evidence。
  4. 写 Habitat adapter，第一版只跑 oracle semantic，不接 detector。
  5. 生成 `habitat_trace.csv` 后复用现有 `UsabilityUpdater`。
  6. 跑 20 episode smoke，检查 UNKNOWN / POSITIVE / FREE 是否都能出现。
  7. 再上 500/1000 episode stress，不要太早调参。

13. 风险和防线

风险 防线
Habitat 安装耗时过长先在独立 conda/env 和 `third_party/` 中隔离，不污染 repo。
Oracle semantic 太理想先把它声明为上界实验，下一阶段再替换 detector。
FREE 条件过严导致 UNKNOWN 过高报告 UNKNOWN ratio，不把保守当成功。
参数阈值被质疑做 threshold sweep，报告敏感性而不是单点数值。
算力不足先 trace 离线化：Habitat 生成 trace，算法可重复 replay。
