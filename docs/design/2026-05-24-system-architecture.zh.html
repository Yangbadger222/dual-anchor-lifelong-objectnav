硬件解耦版 Dual-Anchor Lifelong ObjectNav 系统架构

先把 ObjectNav 核心系统从实车中解耦出来，用离线地图、fake target、回放数据和确定性测试跑通，再通过 ROS 2/Nav2/传感器 adapter 接入真实车。这样系统更泛化，实验更可复现，论文叙事也更强。

核心结论

当前研究方向应该收敛为：一个硬件无关的 Dual-Anchor Lifelong Semantic ObjectNav 系统。核心系统负责目标导航状态机、frontier 选择、长期语义记忆、双锚点表示、到达验证和实验日志；真实车只通过 adapter 提供地图、位姿、传感器观测和 Nav2 执行能力。

一句话论文叙事： 我们不是把某个视觉模型接到小车上，而是提出一套可脱离硬件开发、可回放验证、可接入真实 ROS 2 自主车的双锚点长期语义 ObjectNav 系统。
第一优先级 离线最小闭环：goal -> memory -> frontier -> fake object -> verifier -> memory reuse。
核心贡献 Dual-anchor semantic memory + memory-aware frontier scoring + stale repair。
工程策略 核心逻辑不依赖具体车、相机、RTK、地图路径或 launch 文件。
投稿准备 baseline、消融、日志、失败案例和多 session 实验从第一版就设计进去。

为什么先脱离实车

算法问题更清楚

如果直接在车上开发，定位漂移、相机标定、Nav2 恢复行为和硬件安全会混在一起。离线先跑通，可以先证明 ObjectNav 逻辑本身正确。

实验更可复现

固定地图、固定目标、固定 baseline、固定随机种子，才能让 success、路径长度、time-to-success 和 memory reuse 这些指标可比较。

论文更像系统贡献

硬件无关边界能证明这不是单车 demo，而是一套可迁移到不同 SLAM/Nav2 底座的 ObjectNav 框架。

前沿相关工作定位

2024-2026 年的 ObjectNav 和开放词汇机器人系统已经明显转向 foundation-model semantics、显式记忆、frontier reasoning 和系统级组合。我们的方向最接近 lifelong semantic memory，但不能只说“用了记忆”；真正要做深的是长期运行中记忆如何被验证、失效、修复，并且如何跨 indoor map 与 outdoor ENU/RTK 锚点保持可信。

工作 对我们的启发 我们的差异
OK-Robot 语义记忆、导航 primitive 和真实机器人 heuristics 的系统组合很关键。 它主要使用预扫描静态记忆做 pick-and-drop；我们做在线 ObjectNav、记忆修复和双锚点。
GOAT Lifelong、multi-modal、instance-aware semantic memory 已经是强相关方向。 我们第一阶段聚焦坐标锚点可靠性、stale/missing/relocation 状态机和 ROS/Nav2/RTK adapter。
3D-Mem 3D memory snapshot 和 frontier snapshot 说明 memory 不应只有标签和坐标。 我们先用可验证的 symbolic/SQLite memory 跑通闭环，再把 snapshot/VLM memory 作为后续模块接入。
DynaMem 动态场景里物体出现、消失、移动是核心问题。 我们把动态变化转成可审计的 verifier 状态、trial log 和 anchor-aware memory，而不是只做在线地图。
OpenIN 同类多实例和移动物体需要 instance-level 关系记忆。 Phase 1A 只记录保守的 possible_relocation_of，不急着把新旧目标强行合并。
SCOPE / R2F frontier 可以有语义价值，但大模型频繁调用会影响实时性。 语义 frontier scoring 只作为低频可替换模块；高频控制依然依赖缓存、几何和传统导航约束。
SysNav / TrajRAG / NavFoM 系统解耦、轨迹经验检索、跨 embodiment navigation foundation model 都在成为主线。 我们的落点是 dual-anchor lifelong memory：把 object、viewpoint、frontier、anchor 和失效证据统一存储与评估。

我们主要解决的痛点

记忆会过期

真实环境不是静态 benchmark。系统必须处理 stale、suspect_missing、missing 和 relocation evidence，而不是把旧坐标当真理。

看不到不等于消失

目标可能被遮挡、掉出 FOV、定位有误、costmap 不让车靠近，也可能真的被移走。两次确认和 yaw scan 能把这些情况先分层，而不是一次失败就下结论。

模型不能进 10Hz 闭环

VLM/LLM 适合低频语义推理、frontier 解释和查询消歧，不适合直接接管高频重规划、避障或 Nav2 控制。

目标点不是物体中心

机器人需要能到达、能看见、姿态合适的 verification viewpoint；这比“投影出物体坐标”更接近真实 ObjectNav。

坐标锚点会不可靠

室内 FAST-LIO2/PGO 地图与室外 RTK/ENU 在门口可能跳变。记忆必须保留 native anchor 和 covariance，等 transform 质量足够再融合。

论文结果要可审计

trial event、候选分数、memory state transition 和 failure label 必须从第一版就记录，否则后续很难支撑可信论文结论。

核心研究问题： 机器人如何跨 session 复用语义 ObjectNav 记忆，同时抵抗 stale objects、missing targets、坐标锚点不确定性和真实机器人 adapter 噪声？

什么阶段接入模型

我的判断是：不要在 Phase 1A 接入真实 detector 或 VLM。第一阶段的价值是证明状态机、frontier、verification viewpoint、SQLite memory 和 trial metrics 是正确的。模型应该作为 adapter 逐步接入，而不是一开始就成为系统正确性的来源。

阶段 模型策略 原因
Phase 1A 不接 learned model；使用 hidden scene truth 触发 fake observation。 先隔离并验证 ObjectNav core，不让 perception noise 掩盖架构问题。
Phase 1B / Phase 2 默认仍走确定性路径；可用记录图片做 closed-set perception side experiment。 先检查 anchor、projection、memory schema，而不是追求开放词汇效果。
Phase 4 补齐 model-free 和 model-light baseline。 论文必须知道 memory/verifier/frontier 各自贡献了什么。
Phase 5 首次正式接 detector、segmenter、embedding、arrival verifier，但只在 offline/replay 中评估。 用保存的图像、视频或 rosbag 衡量 precision/recall、投影误差和验证准确率。
Phase 6 真实车接感知 adapter，异步、限频、带 source metadata。 模型输出是 evidence record，不是直接控制命令。
Phase 7+ VLM/LLM/VLA 可用于低频 semantic frontier scoring、query disambiguation 或候选解释。 大模型适合高层语义决策，不应成为局部避障或高频重规划的必要组件。
接入模型的门槛： Phase 1A 四个 deterministic runs 必须稳定通过；接口测试必须覆盖 ObjectObservationSource 和 ArrivalVerifier；回放数据必须有人工检查标签；模型输出必须携带 confidence、timestamp、anchor_id、source 和 failure reason。

三层架构

Layer 1: ObjectNav Core 状态机、frontier、目标选择、语义记忆、verifier、trial logger。
->
Layer 2: Replay / Simulation 离线 grid、fake object、图片/rosbag 回放、确定性 baseline。
->
Layer 3: Robot Adapters ROS 2 topic/action/service、Nav2、TF、相机、点云、RTK/ENU。
关键边界： core 只认识抽象接口和稳定数据结构，不直接读取某台车的 topic 名、设备路径、地图路径或 launch 参数。

接口边界

接口 职责 第一版来源
MapProvider 提供 occupancy-like grid、resolution、origin、free/occupied/unknown cells。 离线 fixture；后续接 /global_costmap/costmap。
PoseProvider 提供机器人当前 pose、时间戳、定位质量和 covariance。 离线轨迹；后续接 TF/PGO/localizer。
ObjectObservationSource 提供目标类别、置信度、pose estimate、detector name、anchor type。 fake target；后续接 YOLO/YOLO-World 和 object projector。
MemoryStore 查询和更新 object、place、frontier、anchor、session memory。 SQLite 优先，极小原型可先 JSON。
NavigationClient 发送、取消和回报导航目标。 离线 navigator；后续接 Nav2 NavigateToPose。
ArrivalVerifier 到达目标附近后返回 verified、not_found 或 ambiguous。 fake verifier；后续接近距离图像检测。

数据流

  1. 输入目标，例如 trash_bin。
  2. ObjectNavManager 查询语义记忆。
  3. 如果有可靠记忆，生成 memory target；如果没有，进入 frontier selection。
  4. GoalSelector 综合 target belief、information gain、memory prior、path cost、revisit penalty、anchor uncertainty 和 stale risk 打分。
  5. NavigationClient 执行选中的目标点。
  6. 导航过程中如果观测到目标，允许取消 frontier 并切换到 object target。
  7. 到达后 ArrivalVerifier 做确认。
  8. MemoryStore 更新为 fresh、verified、stale、missing 或 ambiguous。
  9. TrialLogger 记录每次状态切换、候选分数、导航结果、验证结果和指标。

Phase 1A

Phase 1A：室内饮水机闭环

第一阶段工程上先实现室内单锚点，但接口必须从一开始支持 anchor abstraction。默认目标是 water_dispenser，场景是单走廊里一个靠墙独立摆放的饮水机，相机假设为固定前视。

设计项 Phase 1A 决策
Anchor 只启用 indoor_map，但 observation 和 memory 都必须保存 anchor_id、anchor_type、frame_id。
Object source ConfigTruthObjectSource 用于可复现测试，ManualInjectedObjectSource 用于 RViz/实车调试，后续替换为视觉检测。
Fake detector 只有机器人进入饮水机可视扇区时才发布 observation：距离、水平 FOV、line of sight 和 object active 状态都要满足。
Navigation target 导航到 verification_viewpoint，不是饮水机本体中心。第一版从饮水机前方约 1.2m 处观察，朝向目标中心。
Memory states observed、verified、reusable、stale、suspect_missing、missing。

实验 Run

Run 名称 目的
A discover_and_verify 空 memory，从探索中发现饮水机，验证成功后写成 reusable memory。
B reuse_same_start 同起点复用 saved viewpoint，证明 memory reuse 能减少探索。
C reuse_different_start 不同起点复用同一个目标记忆，证明不是路线复现。
D missing_and_relocation 先隐藏旧目标触发 suspect_missing -> missing，再把目标移动到新位置并记录 relocation evidence。
Relocation 策略： 第一版不强行判断“是不是同一台饮水机”。旧 object 标记为 missing，新位置 object 标记为 verified，并记录 possible_relocation_of(new_id, old_id) 关系。等后续有视觉外观、尺寸和局部 place descriptor 后再考虑合并。

Fixture 与仿真模型

设计项 决定
地图 straight_corridor_one_water_dispenser_unknown：12.0m x 2.4m 单走廊，起点只知道前 3m，其余走廊初始为 unknown。
Reveal model forward_sector：以机器人朝向展开扇形揭示 unknown cell，mapping FOV 约 120deg，raycast 检查 line of sight。
Fake detector FOV 前视相机检测 FOV 约 70deg，小于 mapping/reveal FOV；地图知道某区域不代表相机一定看到目标。
Frontier goal 选择 frontier 前方 known free 区域中的 reachable viewpoint，朝向 frontier centroid；不直接导航到 raw frontier centroid。
Navigation backend 第一版用 DiscreteStepNavigationClient，接口保留给后续 A* 和 Nav2 NavigateToPose adapter。

Core 工程边界

第一版采用 objectnav_core + 后续 objectnav_ros adapter 的结构。objectnav_core 不 import rclpy，不依赖 ROS message，只处理 Pydantic schema、numpy/grid 和离线仿真接口。ROS topic、TF、Nav2 action 和 RViz marker 都放进后续 adapter。

模块 职责
models Pydantic schema：pose、anchor、object、frontier、navigation、trial event、metrics。
mapping grid、forward-sector reveal、frontier extraction。
planning frontier viewpoint、verification viewpoint、candidate scoring。
memory SQLite store、memory state transitions、JSON snapshot export。
simulation scene config、fake detector、discrete navigation、trial runner。
evaluation trial logger、metrics aggregation、candidate-score records。

Memory 与日志

Phase 1A 使用 SQLite 作为主存储，JSON snapshot 只用于调试和人工阅读。高频 tick 不允许扫全表；SQLite query 只在 task start、memory mutation、replan event 或低频 refresh 触发，tick 阶段只读 active memory cache。

Trial log 记录关键事件和每次 replan 的候选评分，不记录每个 tick。默认 metrics 包括 success、path length、elapsed time、frontier count、repeated exploration ratio、time-to-first-observation、time-to-verify、memory reuse、missing detection、relocation recorded 和 num replans。SQLite query count、cache hit 和模块耗时作为 debug metrics。

Missing 判据： 不能一次看不到就标记 missing。第一次 verification 失败进入 suspect_missing；第二次在原地执行 yaw scan，例如目标朝向 ±25deg，仍看不到才进入 missing。

验证计划

阶段 必须验证什么
Phase 1A frontier extraction 单元测试、memory 状态转移测试、饮水机 fake detector 闭环、同起点/不同起点 memory reuse、missing_and_relocation。
Phase 1B 确认 observation、memory 和 query API 不写死 indoor_map，能接受 outdoor_enu anchor fixture。
Phase 2 单独跑 outdoor_enu anchor 的 ObjectNav 和 memory reuse。
Phase 3 模拟 anchor health 和 transform uncertainty，验证过渡区观测不会被强行提升为可靠记忆。
Phase 4-7 ROS 2 package build、workspace source、bag replay、最后才是真实车 live trial。

论文价值

更泛化

硬件无关 core 让系统不绑定一台车，审稿时更容易被理解为方法和系统架构贡献。

更可消融

frontier、semantic prior、memory、dual anchor、verifier 和 repair 都可以独立打开或关闭。

更可复现

trial log、session config、metrics 和 experiment report 从早期就进入流程，支撑后续论文图表。

风险与控制

风险 控制方式
core 逐渐混入车辆 topic 和路径 代码 review 时检查 import、config、launch 依赖，把车辆细节移到 adapter。
离线跑通但实车失败 在 live trial 前增加 rosbag replay 和 adapter-level tests。
旧记忆把车带到错误位置 arrival verifier 失败后标记 missing，降低记忆权重并回到探索。
baseline 不可比较 固定 map、target、seed、session config，并把所有事件写入 trial log。
