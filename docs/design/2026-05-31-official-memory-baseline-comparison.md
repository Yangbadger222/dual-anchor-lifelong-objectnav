# Design Doc: Official Memory Baseline Comparison

Date: 2026-05-31
Owner: Codex
Status: TargetNav-equated diagnostic complete

## Goal

Create a reproducible official Habitat comparison artifact for the paper-facing
memory table:

- `memory_guided`
- `no_memory`
- `naive_count`

The table must report `SR`, `SPL`, `SoftSPL`, and `DistanceToGoal` only from
Habitat-Lab `env.get_metrics()` summaries, not from lifecycle proxy metrics or
locally recomputed success.

## Non-Goals

- Do not claim leaderboard or SOTA performance from a smoke-sized run.
- Do not make the low-level navigator the paper contribution.
- Do not treat lifecycle action-count/path-length metrics as official SPL.
- Do not hide that `naive_count` requires its own positive-only memory source.
- Do not use Habitat pathfinder, target poses, or route followers in online
  benchmark policy runs.

## Background

The project already has two relevant strands:

1. Official Habitat ObjectNav action-loop runs, where Habitat computes
   `success`, `spl`, `soft_spl`, and `distance_to_goal`.
2. Lifecycle memory modes, where `memory_guided`, `no_memory`, and
   `naive_count` compare long-life memory behavior, but not official SR/SPL.

The user's paper direction is now the upper-layer memory system. That means the
next core experiment should be an official Habitat metric table that compares
memory use against fair non-memory and simple-memory baselines while keeping
navigation behind the same black-box policy boundary.

## System Boundary

This slice owns only comparison orchestration and reporting:

- run or aggregate multiple official ObjectNav policy summaries;
- map paper-facing labels to concrete official policy/config choices;
- verify all rows use official Habitat metric summaries;
- write JSON, CSV, and Markdown table artifacts.

It depends on `run_habitat_official_objectnav_eval(...)` for single-policy
execution and does not change policy behavior.

## Inputs and Outputs

| Direction | Name | Type / Format | Notes |
|---|---|---|---|
| Input | Official run config | CLI args | Config path, dataset path, scene root, split, seed, max episodes, max steps. |
| Input | Memory-guided prior | JSON path | Prior for the proposed memory method. |
| Input | Naive-count prior | JSON path | Must come from a positive-only memory/count source for a fair baseline. |
| Input | Optional existing summaries | `label=summary.json` | Lets the tool aggregate completed Linux runs without rerunning Habitat. |
| Output | Comparison report | `comparison.json` | Full per-label metrics, run directories, policy mapping, caveats. |
| Output | CSV table | `comparison.csv` | Stable flat table for spreadsheet/paper plotting. |
| Output | Markdown table | `comparison.md` | Human-readable SR/SPL table for experiment reports. |

## Interfaces

Planned CLI:

```bash
python -m objectnav_core.cli.run_habitat_official_memory_comparison \
  --output runs/habitat_official_objectnav/memory_baseline_comparison_4ep_20260531_v1 \
  --memory-guided-prior-path runs/.../memory_guided_prior.json \
  --naive-count-prior-path runs/.../naive_count_prior.json \
  --max-episodes 4 \
  --max-steps 100 \
  --detector yolo_world
```

Aggregation-only mode:

```bash
python -m objectnav_core.cli.run_habitat_official_memory_comparison \
  --output runs/habitat_official_objectnav/memory_baseline_table_from_existing \
  --from-summary memory_guided=runs/.../summary.json \
  --from-summary no_memory=runs/.../summary.json \
  --from-summary naive_count=runs/.../summary.json
```

Original default label mapping:

| Label | Official policy | Memory source |
|---|---|---|
| `memory_guided` | configurable, default `memory_active_perception_frontier_targetnav_fmm` | proposed memory prior |
| `no_memory` | `occupancy_frontier` | none |
| `naive_count` | configurable, default `memory_guided_frontier` | positive-only naive-count prior |

The `naive_count` row is valid only if its prior was generated by a documented
positive-only source. The comparison artifact records that source boundary and
keeps the row caveated when the source is unknown.

TargetNav-equated update:

The navigation backend should not be the claimed contribution. The next
comparison uses the same terminal TargetNav backend for every row and changes
only the memory condition:

| Label | Official policy | Memory source | Meaning |
|---|---|---|---|
| `memory_guided` | `memory_active_perception_frontier_targetnav` | proposed memory prior | Uses the proposed lifelong memory, then the shared TargetNav backend. |
| `no_memory` | `no_memory_targetnav` | none | Explores without memory; if current-view detector sees the target, hands off to the same TargetNav backend. |
| `naive_count` | `naive_count_targetnav` | positive-only naive-count prior | Uses simple repeated-positive memory with the same TargetNav backend. |

In simulation, `--targetnav-backend oracle_follower` is a diagnostic stand-in
for the robot's Nav2 terminal controller. The resulting table is not a
leaderboard benchmark claim, but it cleanly tests whether memory improves
ObjectNav once terminal navigation is held fixed.

## Data Flow

1. Build three comparison specs from CLI args or load `label=summary.json`
   inputs.
2. For run mode, create one subdirectory per label and call the official
   evaluator with the mapped policy.
3. Read each `summary.json`.
4. Validate that `official_metrics.measure_source` is
   `habitat.Env.get_metrics` and required measures are present.
5. Extract SR, SPL, SoftSPL, mean distance, episode count, policy, and caveat.
6. Write `comparison.json`, `comparison.csv`, and `comparison.md`.

## Failure Modes

| Failure | Detection | Recovery / Mitigation |
|---|---|---|
| Summary lacks official metrics | validation error | refuse to write a paper-facing table. |
| Mixed split/episode settings | report metadata mismatch | record mismatch and mark comparison caveated. |
| Naive-count prior is missing | CLI validation error in run mode | require explicit prior path or aggregate an existing run. |
| Memory-guided policy uses pathfinder suffix | policy caveat copied into table | keep diagnostic row out of benchmark claims. |
| Smoke table has all-zero SR | metrics still reported | treat as diagnostic and continue improving policy/data. |

## Verification Plan

1. Unit-test aggregation from synthetic official summaries.
2. Unit-test rejection of summaries whose metrics are not from
   `habitat.Env.get_metrics`.
3. Unit-test run-mode orchestration with an injected fake official runner.
4. Unit-test CLI argument parsing and report writes.
5. Run focused local tests and syntax checks.
6. Sync to Linux and run focused tests in conda env `habitat`.
7. Run a small official `val_mini` comparison once a naive-count prior artifact
   exists.

Initial pre-equated diagnostic result:

| Method | SR | SPL | SoftSPL | DistanceToGoal |
|---|---:|---:|---:|---:|
| `memory_guided` | 0.0000 | 0.0000 | 0.0172 | 5.7584 |
| `no_memory` | 0.0000 | 0.0000 | 0.0332 | 5.6376 |
| `naive_count` | 0.0000 | 0.0000 | 0.0010 | 5.8806 |

This first table proved the official comparison pipeline, but it still mixed
different terminal navigation behavior across rows.

TargetNav-equated diagnostic result:

| Method | Policy | SR | SPL | SoftSPL | DistanceToGoal | Caveat |
|---|---|---:|---:|---:|---:|---|
| `memory_guided` | `memory_active_perception_frontier_targetnav` | 0.0000 | 0.0000 | 0.1914 | 5.9202 | `targetnav_oracle_backend_diagnostic` |
| `no_memory` | `no_memory_targetnav` | 0.5000 | 0.4673 | 0.4615 | 2.8931 | `targetnav_oracle_backend_diagnostic` |
| `naive_count` | `naive_count_targetnav` | 0.0000 | 0.0000 | 0.1914 | 5.9202 | `targetnav_oracle_backend_diagnostic` |

This is the cleaner memory-quality diagnostic. It is still not an algorithmic
win: on this tiny smoke, detector-triggered `no_memory_targetnav` solved `2/4`
episodes, while both memory rows failed `0/4` and ended farther from the goal.
Because terminal navigation is shared, the result points back to memory target
selection and write policy rather than controller tuning.

## Research Relevance

This comparison is required for the paper story. It separates the contribution
of the memory system from lower-level navigation by holding the official
evaluation path fixed and reporting:

- how much no-memory search can do;
- how much a simple positive-count memory baseline can do;
- whether the proposed memory system improves official ObjectNav outcomes or
  at least reduces failure modes under the same black-box navigator.

The table is not sufficient by itself. The final paper also needs lifecycle
drift/stale-memory experiments and real-robot evidence through the FASTLIO2/Nav
stack. But without this official SR/SPL table, reviewers will not trust the
simulation comparison.

## Open Questions

- Which memory-guided policy should be the primary row after the low-level
  backend is treated as a black box: FMM, learned local policy, or Nav2-like
  adapter?
- What is the cleanest way to export a positive-only naive-count prior under
  the official discovery protocol?
- Should the first table use a fixed detector cache for reproducibility before
  scaling to larger splits?
- Should the final paper table report both oracle-backend diagnostic results
  and non-oracle backend results, with the oracle table framed as a memory
  quality ablation rather than an official benchmark score?
